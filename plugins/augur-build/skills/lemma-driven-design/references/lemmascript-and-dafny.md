# Lemma-driven design with LemmaScript and Dafny

How we do lemma-driven design in TypeScript and JavaScript: [LemmaScript](https://www.npmjs.com/package/lemmascript) (`lsc`) reads `//@` annotations in the shipped `.ts` and translates each function to [Dafny](https://dafny.org), which proves it; the model and the links are hand-written Dafny. A repo MAY name its scripts differently; its own `CLAUDE.md` and wiki win.

New to it: setup, the annotation grammar, what lsc generates, and a worked example from red to green are in [getting-started.md](getting-started.md). This file is the patterns and gaps for after.

## Files

| Path | Holds |
|------|-------|
| `lemmascript.json` | lsc options. Set `"string-semantics": "javascript-utf16"` so a proof counts what `.length` counts |
| `LemmaScript-files.txt` | Every proved `.ts`, one per line. A file with `//@ verify` MUST be listed |
| `models/<Area>.dfy` | The model: one Dafny `module` per area, hand-written, with its lemmas |
| `models/links/<file>.dfy` | One link file per proved code file: `include`s that file's `.dfy` and the model, then a `<function>MatchesModel` lemma per exported function |
| `<dir>/<file>.ts` | The proved code: `//@ backend dafny` at the top, `//@ verify` in each proved function, `//@ requires` and `//@ ensures` as its spec |
| `<dir>/<file>.dfy.gen` | Generated by lsc. Never edited |
| `<dir>/<file>.dfy` | The generated file plus hand additions, **additions only**. Never shipped in a package |
| `<dir>/<file>.test.ts` (or `tests/`) | Runtime pins: each rule against an oracle, at 100% coverage |

- **No escapes** in hand Dafny (the model, links, `.dfy` additions): no `assume`, `{:axiom}`, `{:verify false}`, `{:trusted}` or `expect`.
- **Never put links in a code `.dfy`.** A hand lemma there conflicts on the next regeneration.
- **One code file per link file.** A link that needs another file's function takes a premise that the import equals the model; that file's own link proves the premise.
- **Verifying all the links in one command** (`dafny verify models/links/*.dfy`) makes them one Dafny program, which works only while no two proved files declare the same top-level name, generated helpers included. Give a copied helper its own name; where two generated files still clash, verify their links in separate commands.

## Commands

| Command | Does |
|---------|------|
| `pnpm exec lsc gen --backend=dafny <file>.ts` | Writes `<file>.dfy.gen`; creates `<file>.dfy` only if it is missing |
| `pnpm exec lsc regen --backend=dafny <file>.ts` | Regenerates and three-way merges into `<file>.dfy` |
| `pnpm exec lsc check --backend=dafny` | Regenerates every listed file, checks each `.dfy` adds only, and verifies the code |
| `dafny verify --unicode-char:false models/*.dfy models/links/*.dfy` | Verifies the model and the links |
| `pnpm proofs` | The repo's script running both of the above; MUST pass before submitting |

Dafny runs locally, not in CI: install it (`brew install dafny`) wherever proved files change.

## After changing a proved file

1. Run `lsc regen` (or `lsc gen`, then rebuild the `.dfy`).
2. If the merge conflicts, or `gen` left the old `.dfy` alone: copy the new `.dfy.gen` to `.dfy` and re-add the hand additions. `git diff --no-index <file>.dfy.gen <file>.dfy` on the previous version lists them.
3. Run the proofs, then the link for that file.

## Naming

- Model functions and predicates are `PascalCase` (`IsSiteId`); code functions are `camelCase` (`isSiteId`); the link lemma is `IsSiteIdMatchesModel`.
- A top-level name MUST NOT repeat across proved files when they verify as one program: give a copied helper its own name.
- Dafny keywords cannot be names (`method`, `label`, `fresh`, `to`, `assigned`): rename the parameter.

## Specs and contracts

- **Small proved functions are lemmas.** Each `ensures` is a fact every caller gets for free. Build many small facts and compose them rather than one large proof.
- **An exported function's contract MUST pin its result exactly** (an iff, or `\result ===` in every case). A function imported from another file reaches the importer only as an axiom carrying its contract, so anything looser hides what it returns.
- **A precondition the data never breaks is still stated**: past it, the code may disagree with JavaScript.
- **An exported contract sees only what the importer can resolve.** A same-file helper or a module constant named in the contract is unresolved in the importer; moving the helper to another file works one level deep, so inline the code instead. The contract must be closed-form (a recursive equation is refused), and an import used only in a contract gets no stub.
- **Proving a negation needs a witness.** To show a `forall` fails or an `exists` holds, assert the case in the body (the two equal elements, the breaking input): the prover does not search for one.
- **Give quantifiers a function to trigger on.** A nested `forall ... exists` over raw character codes can fail to prove; the same property as a named predicate call proves at once.

## Links

- **A link reaches the code's real body**, not just its `ensures`, so it proves the code equal to the model, not merely consistent with its contract.
- **Bridge once, in the model.** When a code-by-code contract has to meet the model's recursive definition, prove that once as a model lemma, and have every link call it.
- **String unions become datatypes.** lsc turns `type Kind = "a" | "b"` into a generated `datatype`; the link maps it into the model's own datatype.
- **A link lemma SHOULD verify in under 10 seconds on its own.** Under the full run's load a borderline one times out.

## Loops

Recursion is the natural way to state a rule, and Dafny proves it, but JavaScript runs it on the stack, one frame per element, and overflows at about 10,000 frames. Anything that walks a string, a list, lines or edges MUST be a loop.

1. In the `.ts`, write a `while` loop and mark the function `//@ pure`, with `//@ invariant` bounds and `//@ decreases` on the loop. lsc emits it as Dafny `function f(...) { f_fun_spec(...) } by method { <the loop> }`, with `f_fun_spec` a bodyless stub.
2. In the `.dfy`, as additions: give `f_fun_spec` the recursive definition (what a recursive `f` would have been, calling `f_fun_spec`), its `decreases`, and its `ensures`.
3. Add the invariant that ties the loop to the spec: `f_fun_spec(s, j) == f_fun_spec(s, i)` for a search, `acc + f_fun_spec(s, j) == f_fun_spec(s, i)` when the loop builds a result, `f_fun_spec(s, j, acc) == f_fun_spec(s, i, start)` when it threads a value. Add `0 <= j` on a loop that counts down.
4. Callers and links keep calling `f`, which is its spec, so they need no change.

Notes:

- **lsc drops `//@ ensures` on a `//@ pure` loop**: it emits no lemma and checks nothing. Put those `ensures` on `f_fun_spec` in the `.dfy`; keep them in the `.ts` as the contract a reader sees.
- **`push`, not a spread.** `acc.push(x)` on a local becomes `acc := acc + [x]`, so the proof is the same, and JavaScript appends in place. `[...acc, x]` copies every time.
- **Test each walk at 100,000 elements** against the oracle.
- **Joining by halves** (recursing on each half of a range) is an alternative to a loop for building a long result: its depth is logarithmic, and it stays an expression a spec can call.

## Regexes and built-ins

- **A regex is a decision, and lsc cannot translate one.** Write it as a code-unit scanner that makes the same leftmost, greedy match, state the regex in the model, and pin the scanner to the original regex in the tests over thousands of generated inputs.
- **Verify the checker, not the producer.** Where a platform built-in does the work (`encodeURIComponent`), call it, and prove a small guard over its output rather than re-implementing it.

## Where lsc differs from JavaScript

Re-check this list on each lsc upgrade.

- **Numbers are not IEEE doubles.** LemmaScript's `number` is an unbounded integer, or an exact real wherever a non-integer literal appears. A proof of float or money arithmetic proves nothing about what runs: keep it to integers.
- **`toLowerCase` translates to an `{:axiom}`.** Lower ASCII with a proved function instead.
- **`const x = arr[k]` becomes an `Option`.** Read fields in place, and write `arr[k]!` where TypeScript's strict index checks need it.
- **A loop without `//@ pure` becomes a method**, which no spec may call; a link to it can only be as strong as its `ensures`.
- **An imported `//@ type x nat` parameter arrives as `int`**: restate `//@ requires x >= 0` where it indexes.
- **A branch no input reaches still counts against 100% branch coverage** (`??` and `?.` count): rule it out with a `requires` or an `ensures` rather than leaving it.
- **`T | null | undefined` becomes one `Option`, silently**: `null` and `undefined` are both `None`. Use one nullable kind per function.
- **`x !== null && f(x)` does not narrow `x`**; only `?:` unwraps it.
- **A reassigned `let` makes a function without `//@ pure` a method**, which a link cannot call inside an expression. Write a `const` chain instead, or, for a loop, mark the function `//@ pure` (its `let`s may then be reassigned in the loop).
- **A brand imported from another package loses its `//@ type`** through the built `.d.ts`: redeclare it locally and pin it with a type test.
- **`bigint` translates faithfully, except `Number(b)`**, which lsc treats as the identity while JavaScript rounds past 2^53.
- **A `decreases` inserted into a generated lemma can break the additions-only check**: put the induction in a helper lemma at the end of the file instead. To use a same-file `ensures`, call `<f>_ensures` as a hand-added line in the body.
- **A real-number literal in a committed `.dfy.gen`** means float arithmetic reached the proof: remove it.

## Tests that pin the runtime

- **Coverage must not depend on what a property-based generator draws.** Give every branch a fixed example as well, and sweep seeds.
- **Exhaustive loops collect, then assert once.** Checking all 65,536 code units with one assertion each is slow enough to time out CI; gather the mismatches and assert the list is empty.
- **Use the real library's error classes in mocks** (`vi.importActual`), or run the library in memory: a hand-made mock hid that field errors never surfaced and that a missing record gave a 500, not a 404.
- **Without a mutation tool,** find unpinned decisions by the break-it step and by reading each branch: every one must change some test's result.

## Checks and measurement

A repo SHOULD measure its proofs, not just run them:

- **Proof coverage per workspace**: proved functions and lines, the share whose functions have their own `ensures` (specced), and the share named in a `…MatchesModel` lemma's `ensures` or called by one (linked). An `include` path does not count as linked. Render-only functions (markup on every path, no decision) are left out; a render function holding a decision is listed until it moves into a rule.
- **Floors only rise.** A drop because code got less proved is fixed by proving more. A drop because code moved up a layer, exactly as proved and linked, resets the giving workspace's floor in the same change, with the move named in the commit. The update command writes lower numbers too, so compare before running it.
- **Structural checks**: every link premise (`requires forall … code(…) == Model.F(…)`) is the `ensures` of some link lemma; each link file includes one code file; the same contract proved in two workspaces fails (prove it once, higher up); no unlisted `//@ verify`; no dead `//@ skip`.
- **Pin Dafny and Z3.** Record both versions in the repo and install the pinned Z3: a Z3 upgrade alone made links time out. Cache proof results by a hash of the file, every file it includes, and the tool versions.
- **Budget the time.** A full run SHOULD finish in under 5 minutes; record each run's time and treat one much slower than its last as a defect. Split a large link into chunks and give the slowest more cores.

## When a proof is slow or fails

- **The function is usually too big.** Split it, and let the tests protect the split.
- **Assert the step.** Name each fact a step needs (`assert f(x) == f_fun_spec(x);`) before the step that uses it; with function-by-method, one unfolding of each side often lines a link up.
- **Split cases explicitly**, and add a small head lemma for a long chain.
- **`{:vcs_split_on_every_assert}`** on a lemma that times out as a whole; **`{:isolate_assertions}`** with each part named once, for a small one.
- **`{:fuel f, 0, 0}`** on a lemma whose time goes into unfolding large mutually recursive bodies it does not need.
- **Never fix a failing proof by changing the spec**: decide which is wrong, as the skill's rules say.
